# O.A.S.I.S. Dashboard — Usability Correction

The latest dashboard redesign is too dense and difficult to scan. It contains too many competing cards, redundant measurements, nested scrolling, and technical details that overwhelm the primary information.

Refactor the existing dashboard to improve information hierarchy and usability.

## Before editing
- Inspect the current dashboard component, data sources, types, styling, and related components.
- Identify which fields represent raw sensor data, processed measurements, LLM outputs, deterministic rule checks, and controller proposals.
- Preserve all working functionality and data bindings.
- Do not replace the page with a static mockup.

## Required layout

### 1. Compact header
Show the page title, selected plant profile, and replay controls in a compact header.

Clearly identify offline replay or simulation mode. Keep the replay timeline and current frame accessible without making them dominate the page.

### 2. Primary plant status
Create one prominent section containing:
- Plant name and growth stage.
- Overall configured-range status.
- A short explanation of what that status means.
- A visible indication of whether the data is live, simulated, or replayed.

Avoid repeating the same status message in multiple places.

### 3. Three primary measurements
Display only the three most relevant measurements as prominent metric cards. For the existing potato profile, these may be air temperature, substrate moisture, and VPD, provided those values are already available.

Each card should show the value, unit, and applicable target range.

Move remaining measurements into a compact, secondary "All sensor readings" section.

### 4. AI assessment
Create a clearly differentiated panel for the actual LLM-generated assessment and its justification.

Display the relevant evidence, recommendation, and uncertainty only when supplied by the real system output.

Do not label deterministic rules-based output as an AI assessment. If the LLM result is missing, show a clear unavailable state.

### 5. Controller proposal and safeguards
Display the proposed adjustments in a compact table with readable labels and units.

Separate:
- Proposed values.
- Deterministic safety checks.
- Human approval status, if implemented.
- Confirmed execution status, if implemented.

Preserve the distinction between a proposed action and an action actually sent to hardware.

Move detailed rule logs into a collapsible "Technical details" section.

### 6. Sensor history
Give the sensor chart a dedicated, readable section with:
- A clear chart title and metric selector.
- Readable axes and units.
- Target bands where available.
- A timeline and replay controls directly below the chart.
- No unnecessary nested scrollbar.

Keep the chart connected to the existing data and selected replay frame.

## Visual design
Use a restrained scientific-monitoring aesthetic:
- Deep navy background.
- Clearly differentiated surfaces.
- Muted green for healthy states.
- Amber or red for appropriate warning states.
- High-contrast text and readable labels.
- Consistent spacing and typography.
- Fewer borders, fewer nested cards, and no decorative clutter.

Avoid shrinking all content to fit above the fold. Prefer a clear vertical hierarchy and natural scrolling.

## Acceptance criteria
- A first-time visitor can identify the selected plant, overall status, and three primary readings within five seconds.
- The AI assessment is visually distinct from deterministic rule checks.
- The user can find the controller proposal without scanning multiple panels.
- The sensor chart and timeline are easy to locate and operate.
- Technical logs remain accessible but do not dominate the page.
- Existing interactions, calculations, replay behavior, and data sources continue to work.
- All simulated data is labelled honestly.

Implement the refactor in the existing codebase. At the end, list the components changed, confirm which existing functions and data bindings were preserved, and report any checks that could not be completed.
